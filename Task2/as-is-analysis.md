## Анализ артефактов, использованных для восстановления AS-IS

### Источники и их роль

|  |  |  |
| --- | --- | --- |
| **Артефакт** | **Информация** | **Комментарии** |
| Постановка задачи | Бизнес-контекст, история развития, стек, инфраструктура, цели, ограничения | Нет конкретных метрик, схем, деталей реализации |
| Диаграмма AS iS | Верхнеуровневая схема компонентов, внешние зависимости, потоки | Может быть неполной, не отражает фактические обходы |
| Стенограмма интервью — Бизнес-заказчик направления цифровых продаж | Бизнес-цели, приоритеты, риск-аппетит, критерии успеха, ограничения | Нет технических деталей |
| Стенограмма интервью — Руководитель клиентской поддержки | Клиентские боли, ручные операции, проблемы статусов, наблюдаемости | Взгляд снаружи, не технические причины |
| Стенограмма интервью — Технический лидер монолитного ядра | Устройство монолита, распределение логики, скрытые зависимости, Oracle packages, fallback | Локальная экспертиза, может быть неполной по другим доменам |
| Стенограмма интервью 2 — Разработчик логистических и партнёрских интеграций | Смешанные интеграции, распределение правил маршрутизации, проблемы дедупликации | Фокус на логистике |
| Стенограмма интервью 3 — Разработчик аналитики и отчётности | Отсутствие канонической модели, зависимость от Oracle, проблемы качества данных | Взгляд аналитики, не операционный контур |
| Фрагмент кода OrderProcessingService.java | Реальные технические решения: смешение ответственности, fallback на Oracle package, синхронные вызовы, работа со staging, длинная транзакция | Один фрагмент, не вся система |

### Что подтверждено источниками

|  |  |
| --- | --- |
| **Гипотеза** | **Подтверждение** |
| Монолит — центральный оркестратор | Технический лидер: «проще сказать, за что оно не отвечает»; |
| Цена/промо реализованы неоднородно | Технический лидер: три механизма + исключения; |
| Статусы распределены | Технический лидер: Java, batch, Oracle, ручные интерфейсы; поддержка: разрыв между статусами |
| Интеграции смешанные | Логистика: REST, очереди, таблицы, batch; |
| Oracle — узкое место | Технический лидер: длинные транзакции, тяжёлые SQL; аналитика: прямые SQL в операционную БД |
| Ручные вмешательства | Поддержка: админ-интерфейсы; Tech Lead: «иначе заказы зависали бы до утра» |
| Нет единой модели данных | Аналитика: разные витрины, разные цифры; поддержка: карточка не источник правды |
| Скрытая логика в Oracle | Tech Lead: «половина фактической логики сидит в БД» |
| Разные ветки по каналам | Tech Lead: «одинаковый заказ — разный» |

### Что осталось противоречивым или неполным

|  |  |
| --- | --- |
| **Вопрос** | **Противоречие / пробел** |
| Частота ручных корректировок | Поддержка говорит «чаще, чем хотелось бы», но нет цифр |
| Доля заказов, идущих через fallback промо | Tech Lead: «бизнес терпит», но нет метрики |
| Реальный процент заказов, затронутых раздельная доставка | Поддержка: «частая боль», логистика: «куча специальных случаев» — нет точных данных |
| Вклад аналитики в нагрузку на Oracle | Аналитика: «заметно в пиковые окна», но нет измерений |
| Количество статусов и их фактическая семантика | Tech Lead даёт примерный список, но «куча ответвлений» без полной карты |
| Состояние архивации данных | О компании: «реализовано частично», техлид не уточняет |
| Точные SLA/SLO, RTO/RPO | Не заданы |
| Бюджет и сроки этапов трансформации | Бизнес: «последовательные инвестиции», но без цифр |

### Ключевые выводы для дальнейшего анализа

1.  **Границы доменов размыты**: цена, промо, статусы, логистика пересекаются в монолите, Oracle и сервисах.
2.  **Oracle — не только БД**: packages, staging, общие таблицы, скрытая логика.
3.  **Интеграции не унифицированы**: четыре разных способа обмена, нет единого контракта.
4.  **Слабая наблюдаемость**: корреляционные идентификаторы есть не везде, история собирается вручную.
5.  **Аналитика — индикатор архитектурных проблем**: расхождение цифр = расхождение моделей.
6.  **Трансформация должна начинаться с безопасных зон**: чтение статусов, часть промо, отдельные интеграции, post-order processing.
7.  **Зона высокого риска – сheckout (оформление заказа) и payment orchestration (проведение платежа)**: изменять только после анализа связностей, в т.ч. скрытых.
